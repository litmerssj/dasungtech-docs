# ANASA 저장 프로시저 → ORM 전환 타당성·비용 평가

| 항목 | 내용 |
| --- | --- |
| 작성일 | 2026-08-28 |
| 대상 | `be_anasa`의 저장 프로시저(SP) 의존 API를 SQLAlchemy ORM 중심으로 전환 |
| 백엔드 기준 | `be_anasa` `origin/develop` `7ee1279991e235ddba42c6913670f1065b2a502a` |
| 역설계 기준 | `anasa-procedure-reverse-engineering` `origin/main` `18369246bc11c71c41a52e5c2e5fcafc0b934317` |
| 공수 단가 | 1인일 80만원, VAT 별도 계획 단가 |
| 금액 성격 | 고정 견적이 아닌 대표 PoC 전 계획 범위 |

## 1. 결론

ANASA의 모든 저장 프로시저를 ORM으로 한 번에 교체하는 것은 기술적으로 가능하지만, 현재 목적이 SQL Server 라이선스 절감이라면 경제성이 없다.

핵심 판단은 다음과 같다.

1. **SP를 ORM으로 바꾸고 MSSQL을 유지하면 SQL Server 라이선스 비용은 그대로다.**
2. 라이선스 비용을 없애려면 PostgreSQL 등으로 DB 엔진까지 완전히 전환해야 한다.
3. 현재 959개 업무 API 중 SP 의존이 확인된 API는 747개(77.9%)다.
4. 최신 화면 계보에는 고유 active SP 407개가 연결돼 있고, 라이브 DB 전체에는 active SP 1,815개가 있다.
5. 현재 API 범위의 SP → ORM 전면 전환은 약 1,500~3,000인일, VAT 포함 약 13.2~26.4억원의 계획 범위다.
6. PostgreSQL 전환까지 포함하면 총 1,800~3,700인일, VAT 포함 약 15.8~32.6억원 수준이다.
7. 신규 Standard 4코어 영구 라이선스 약 1,215만원과 비교하면 최소 전환비가 약 130배다.

따라서 현재 권장안은 **MSSQL과 검증된 SP를 유지하고, 신규 기능과 변경 빈도가 높은 단순 CRUD부터 ORM-first로 개발하는 단계적 혼합 전략**이다. 전면 전환은 라이선스 절감 외에 Microsoft 종속 해소, 전사 PostgreSQL 표준화 또는 장기 제품화라는 별도 전략 목표가 있을 때만 추진한다.

## 2. 범위 정의

“모든 SP를 ORM으로 교체”는 두 가지로 해석할 수 있으므로 구분해야 한다.

| 범위 | 대상 | 판단 |
| --- | --- | --- |
| 현재 ANASA API의 SP 제거 | 현재 업무 API가 실제 호출하는 SP를 애플리케이션 로직과 ORM으로 대체 | 이번 비용 산정의 기본 범위 |
| 라이브 DB의 전체 SP 제거 | 라이브 DB active SP 1,815개 전부를 재작성 또는 폐기 | 미사용 레거시까지 포함될 수 있어 비권장 |

현재 화면에서 확인된 고유 SP는 407개지만, 백엔드에는 현재 FE가 호출하지 않는 API와 내부·외부 연동이 있을 수 있다. 반대로 라이브 DB 1,815개를 모두 다시 만드는 것은 사용되지 않는 레거시 SP까지 비용을 지불할 가능성이 크다.

전면 전환 전에 최소 4~8주의 운영 호출 계측으로 다음을 분류해야 한다.

- 실제 호출 SP
- 화면·배치·외부 연동이 공유하는 SP
- 호출되지 않는 SP
- 법적·회계·감사 목적으로 보존해야 하는 SP
- 즉시 폐기 가능한 SP

미사용 SP는 ORM으로 다시 만들지 않고 폐기 후보로 관리하는 것이 맞다.

`be_anasa`의 활성 FastAPI decorator를 정적 분석하고 route → service → repository 호출 경로를 추적했다.

| --- | ---: | ---: |

| SP-free SQLAlchemy + text/hint 혼합 | 81개 | 8.2% |
| 직접 SQL만 확인 | 2개 | 0.2% |

| **합계** | **991개** | **100%** |

QA fixture API, core health/template API, SP 인덱스와 캐시 관리용 기술 API를 제외한 959개를 업무 API 분모로 사용했다.

| 구분 | 업무 API | 959개 대비 | 해석 |
| --- | ---: | ---: | --- |
| SP만 확인 | 614개 | 64.0% | SP 호출 경로가 있고 ORM DB 조작은 확인되지 않음 |
| SP + ORM 혼합 | 133개 | 13.9% | 한 API 경로에서 SP와 ORM을 함께 사용 |
| **SP 의존 합계** | **747개** | **77.9%** | SP 제거 시 변경 대상 |
| **엄격한 ORM-only** | **135개** | **14.1%** | SP와 textual SQL 없이 ORM DB 조작 확인 |
| ORM + textual SQL/hint, SP 없음 | 63개 | 6.6% | 넓은 의미의 SP-free SQLAlchemy 구현 |
| 직접 SQL, SP 없음 | 2개 | 0.2% | ORM 전환으로 보지 않음 |
| DB 미사용 또는 판정 보류 | 12개 | 1.3% | 분모에는 포함하되 ORM으로 집계하지 않음 |

따라서 질문에 대한 답은 다음과 같다.

> **현재 엄격하게 ORM만 사용하는 업무 API는 135/959개, 약 14.1%다.**
>
> SP를 쓰지 않지만 SQLAlchemy `text()`나 DB별 hint가 섞인 구현까지 포함하면 198/959개, 약 20.6%다.

이 값은 현재 구현 방식의 비율이다. 해당 API가 과거 SP에서 ORM으로 “교체된 것”인지, 처음부터 ORM으로 개발됐는지는 Git 이력을 API별로 조사하지 않았으므로 단정하지 않는다.

### 3.3 판정 방법과 한계

- 주석 처리된 decorator는 제외하고 HTTP method/path 조합을 한 API 작업으로 계산했다.
- 공용 DB session이 특정 캐시 경계에서 호출하는 `sys.sp_getapplock`은 업무 SP가 아니므로 제외했다.
- `StoredProcedureExecutor`, `exec_text*`, `execute_procedure*`, `procedure_name`과 `EXEC` 호출을 SP 표식으로 사용했다.
- SQLAlchemy `select`, session `query/execute/add/delete`와 모델 조작을 ORM 표식으로 사용했다.
- SQLAlchemy `text()`와 dialect별 SQL 조각은 엄격한 ORM-only에서 제외했다.
- 동적 dispatch, 런타임 monkey patch, 외부 서비스와 문자열 조합은 정적 분석에서 누락될 수 있다.
- API 개수는 복잡도를 나타내지 않는다. 단순 조회 API 1개와 재고·마감 API 1개의 전환 난도는 크게 다르다.

따라서 14.1%는 재무제표 수준의 확정 수치가 아니라 코드 기준의 재현 가능한 정적 분석값이며, 전환 착수 전에는 대표 표본과 런타임 SQL 추적으로 검증한다.

## 5. SP → ORM 전환 단점과 위험

| 위험 | ANASA 영향 |
| --- | --- |
| 숨은 업무 규칙 누락 | 오래된 SP의 분기·채번·이력·오류 메시지가 요구사항 문서에 없을 수 있음 |
| 데이터 정합성 회귀 | 주문·출고·재고·마감의 여러 테이블 변경 순서가 달라질 수 있음 |
| 성능 저하 | 한 번의 set 기반 SP가 여러 ORM round trip과 N+1 쿼리로 바뀔 수 있음 |
| 교차 DB 트랜잭션 | 254개 교차 DB 관계를 앱 계층에서 안전하게 재현하기 어려움 |
| 동시성·잠금 차이 | SP의 lock hint, isolation, 자체 transaction과 오류 반환을 재설계해야 함 |
| 결과 계약 변화 | 컬럼명·순서·NULL·다중 결과 집합이 FE DTO와 출력물을 깨뜨릴 수 있음 |
| 장기 이중 운영 | SP와 ORM 두 경로를 비교하는 동안 개발·운영비가 중복됨 |
| 장애 범위 증가 | 검증되지 않은 전면 교체는 안정적인 기존 업무까지 동시에 위험하게 만듦 |
| ORM 만능화 위험 | 복잡한 집계·대량 처리에는 ORM보다 최적화된 SQL이 더 적합할 수 있음 |

ORM으로 옮긴 뒤에도 SQL과 인덱스 설계는 필요하다. ORM은 SQL을 없애는 기술이 아니라 SQL 생성과 객체 매핑을 애플리케이션에서 관리하는 방식이다.

### 6.3 ORM 전환 후 PostgreSQL까지 이전

PostgreSQL 이전에는 다음 작업이 추가된다.

- SQL Server 데이터 타입·정렬 규칙·날짜·숫자 동작 변환

- 약 279GB 데이터 이동, 증분 동기화와 최종 절체
- 인덱스·실행계획·잠금·격리 수준 재튜닝
- SQL Server 전용 함수, hint, TVP와 동적 SQL 제거
- 백업·복구·모니터링·HA 운영 체계 교체

| 구분 | 계획 공수 | VAT 별도 | VAT 포함 |

이는 계획 범위다. 대표 PoC에서 복잡도별 실제 인일을 측정한 뒤 고정 견적 또는 단계별 상한을 정해야 한다.

## 7. 라이선스 절감과 회수기간

### SP → ORM, MSSQL 유지

SQL Server는 그대로이므로 라이선스 절감액은 **0원**이다. 전환비는 유지보수성과 개발 생산성을 위한 투자이지 라이선스 절감 투자가 아니다.

### PostgreSQL까지 전환

현재 최종 견적의 SQL Server Standard 4코어 영구 라이선스는 VAT 포함 약 1,215만원이다.

| 비교 | 금액 |
| --- | ---: |
| PostgreSQL 포함 전면 전환 최소비용 | 약 15.8억원 |
| 회피 가능한 신규 영구 라이선스 | 약 0.1215억원 |
| 전환비 / 라이선스 | 약 130배 |

연간 구독 공개가 기준 절감액은 VAT 포함 연 약 437만원이다. 최소 전환비를 라이선스 구독료만으로 회수하려면 300년을 훨씬 넘는다. DB EC2·EBS·백업 비용은 PostgreSQL에서도 계속 필요하므로 인프라 전체 66만원/월을 절감액으로 잡으면 안 된다.

기존 전산실 라이선스를 AWS에서 재사용할 수 있다면 회피 가능한 신규 라이선스 비용마저 줄거나 0원이 된다. 따라서 라이선스 비용만으로 전면 전환을 승인할 근거는 없다.

## 8. 권장 전환 전략

### 1단계 — 현재 운영 안정화

- 기존 SQL Server 권리와 AWS 이전 가능성을 먼저 확인한다.
- 운영 라이선스, 백업·복원, 모니터링과 HA 결정을 먼저 완료한다.
- SP와 백엔드 정의 drift를 배포 gate로 관리한다.

### 2단계 — ORM-first 원칙

- 신규 단순 CRUD는 ORM으로 구현한다.
- 기존 SP를 수정해야 하는 기능은 ORM 대체 비용을 함께 비교한다.
- 복잡한 집계·대량 처리·마감 SP는 성능과 정합성 근거 없이 옮기지 않는다.

### 3단계 — 대표 PoC

다음 표본 10~15개를 선정한다.

- 단순 단건 조회
- pagination·검색 조회
- 단일 테이블 CRUD
- 여러 테이블 저장
- 교차 DB 조회
- 자체 transaction·오류 반환 SP
- 동적 SQL·임시 테이블·다중 결과 집합
- 주문·출고·재고·마감 핵심 업무

기존 SP와 ORM을 같은 snapshot에 실행해 결과 행, 합계, 오류, lock, 실행시간과 실행계획을 비교한다. PoC 후 전체 공수 오차범위를 다시 계산한다.

### 4단계 — Strangler 방식 선별 전환

- API 계약은 유지하고 repository 내부 구현만 SP에서 ORM으로 교체한다.
- 읽기 API부터 shadow query로 결과를 비교한다.
- 쓰기는 transaction별로 한 경로만 원본 쓰기를 담당한다.
- 업무 흐름 단위로 전환하고 즉시 롤백 가능한 기간을 둔다.
- 운영 호출이 없는 SP는 재작성하지 않고 폐기 절차로 보낸다.

## 9. 최종 의사결정

| 목적 | 권고 |
| --- | --- |
| SQL Server 라이선스 1,215만원 절감 | 전면 전환 비권장 |
| 현재 ERP 안정 운영 | MSSQL + 검증된 SP 유지 |
| 유지보수 편의 개선 | 변경 빈도가 높은 단순 SP부터 선별 ORM 전환 |
| 신규 기능 개발 | ORM-first, 복잡 SQL은 repository에 명시적으로 관리 |
| 장기 PostgreSQL 표준화 | 대표 PoC와 업무 영역별 단계 전환 후 재승인 |
| 라이브 SP 전체 제거 | 미사용 SP 호출 계측 전에는 승인하지 않음 |

현재 ANASA는 기능 추가·변경이 자주 일어나지 않을 것으로 예상된다. 이 조건에서는 전면 재개발로 얻는 유지보수 편익도 작아지므로, 전환의 경제성은 더욱 낮다.

> **최종 권고: 지금은 전면 SP → ORM 교체를 하지 않는다. 기존 라이선스 실사와 운영 안정화를 우선하고, 신규·고변경 CRUD만 ORM-first로 전환한다. PostgreSQL 전환은 라이선스 절감이 아니라 장기 플랫폼 전략으로 별도 승인한다.**
