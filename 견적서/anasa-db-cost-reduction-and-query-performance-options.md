## 1. 결론 요약

저장 프로시저라는 기술 자체가 MSSQL을 강제하지는 않는다. PostgreSQL, MySQL 등도 저장 프로시저나 함수 기능을 제공한다. 다만 **현재 T-SQL 저장 프로시저의 코드와 호출 계약을 거의 그대로 유지하려면 SQL Server 계열이 사실상 필요하다.**

최신 역설계 기준 ANASA 라이브 DB에는 활성 저장 프로시저 1,815개가 있고, 현재 화면에 연결된 고유 active SP도 407개다. DB 엔진을 변경하면 단순 문법 변환뿐 아니라 TVP, 동적 SQL, 임시 테이블, 트랜잭션, 오류 반환, 교차 DB 참조와 결과 형식을 다시 검증해야 한다. 따라서 DB 전환은 라이선스만 없애는 단순 비용 절감 작업으로 보기 어렵다.

현 시점 권장 방향은 다음과 같다.

1. MSSQL은 우선 유지한다.
2. 실제 사용자·장치가 적다면 `Server+CAL` 라이선스를 코어 구독과 비교한다.
3. 고객사가 보유한 기존 SQL Server 라이선스와 Software Assurance, License Mobility 적용 가능성을 확인한다.
4. 조회 성능은 쿼리·인덱스 개선부터 진행한다.
5. Redis 분리, EBS 성능 증설, DB 서버 증설은 측정 결과에 따른 선택 옵션으로 둔다.

> **핵심 판단:** 인덱스와 쿼리 최적화는 SQL Server 라이선스 비용을 올리지 않는다. 비용이 크게 증가하는 시점은 DB를 8 vCPU로 증설하거나 조회 전용 DB를 추가할 때다.

## 2. 저장 프로시저를 유지하면 MSSQL이 필수인가

`저장 프로시저 유지`의 의미에 따라 답이 달라진다.

- 업무 규칙과 반환 결과만 유지한다면 다른 DB로 재작성할 수 있다.
- 현재 T-SQL 원문과 애플리케이션 호출 계약을 거의 그대로 유지한다면 SQL Server 또는 충분한 T-SQL 호환 계층이 필요하다.

| 선택지 | 기존 SP 처리 | 비용 특성 | ANASA 판단 |
| --- | --- | --- | --- |
| SQL Server Standard 유지 | 대부분 그대로 사용 | 라이선스 비용 계속 발생 | 전환 위험이 가장 낮다. 라이선스 방식과 인프라 계약으로 먼저 절감한다. |
| Azure SQL Managed Instance 또는 RDS for SQL Server | 대부분 호환되지만 사전 검사 필요 | 라이선스 포함형 관리 서비스 비용 | 운영 자동화 장점은 있으나 반드시 더 저렴하지는 않다. 기능 제한과 총비용을 별도 산정해야 한다. |
| Babelfish for Aurora PostgreSQL | T-SQL 일부 호환 | SQL Server 라이선스 제거 가능 | 호환되지 않는 문법과 기능은 재작성해야 한다. 화면 연결 고유 SP 407개에 대한 호환성 검사가 필요하다. |
| PostgreSQL 또는 MySQL 전환 | 대부분 재작성 | DB 라이선스는 절감 | 장기 전략으로는 가능하지만 단순 비용 절감 프로젝트로 보기 어렵다. |
| SQL Server Express | SP 사용 가능 | 무료 | DB당 데이터 10GB 제한으로 MISTO, MISPD, MISTW를 수용할 수 없다. |
| Developer 또는 Evaluation | SP 사용 가능 | 무료 | 실제 운영 사용이 허용되지 않는다. |
| SQL Server Web | SP 사용 가능 | 호스팅·SPLA 채널 | 일반 ERP 운영 목적에는 부적합하다. |

### 2.1 다른 DB로 바꿀 때 다시 확인해야 하는 항목

- T-SQL 전용 구문과 SQL Server 함수
- TVP와 다중 결과 집합
- `TRY/CATCH`, `RAISERROR`, 반환 코드와 오류 메시지 계약
- 임시 테이블, 테이블 변수와 동적 SQL
- 프로시저 내부 트랜잭션과 애플리케이션 트랜잭션 경계
- 교차 DB 참조와 3-part name
- SQL Server Agent 작업과 배치 실행
- 데이터 타입, 정렬 규칙, 날짜·숫자 변환 결과
- 프로시저 결과의 컬럼명, 순서와 null 처리
- 동시성, 잠금과 격리 수준 차이

### 2.2 DB 전환의 비용 회수 판단

현재 4코어 Standard 연간 구독료는 공개가 기준 연 $2,836이며, VAT를 포함한 3년 라이선스 비용은 약 1,310만원이다.

```text
$2,836 × 3년 × VAT 1.10 × 1,400원 = 약 1,310만원
```

인일 단가를 80만원으로 가정하면 3년 라이선스 비용은 약 16인일에 해당한다. 화면 연결 고유 SP 407개를 분석하고, 변환하고, 회귀 테스트하는 작업은 이 범위를 크게 넘는다.

따라서 DB 전환은 다음과 같은 추가 목적이 있을 때 별도 프로젝트로 검토하는 것이 적절하다.

- 장기적인 Microsoft 종속 완화
- 전사 PostgreSQL 표준화
- 향후 확장 구조 변경
- 관리형 DB 전환과 운영 인력 절감
- 신규 기능은 ORM 중심으로 개발하고 기존 SP 의존도를 단계적으로 축소하는 계획

## 3. DB 엔진을 바꾸지 않는 비용 절감 옵션

### 3.1 기존 라이선스와 계약 권리 확인

가장 먼저 고객사가 다음 권리를 보유했는지 확인한다.

- 기존 SQL Server Standard 코어 또는 Server 라이선스
- Software Assurance
- License Mobility 또는 AWS 반입 가능 조건
- Microsoft CSP 할인 계약
- 장기 계약 또는 볼륨 라이선스 할인

기존 적격 라이선스를 증분 비용 없이 사용할 수 있다면 3배 성장 기준 연간 운영비는 약 1,156만원에서 약 720만원으로 낮아질 수 있다. 3년간 약 1,310만원을 절감하는 효과다.

다만 AWS EC2에 기존 라이선스를 적용할 수 있는지는 라이선스 종류와 계약 조건에 따라 다르므로 Microsoft CSP 확인이 필요하다.

### 3.2 Standard Server+CAL

SQL Server Standard는 코어 방식 외에 Server+CAL 방식도 제공한다. 접속자가 내부의 식별 가능한 사용자 또는 장치로 한정되고 수가 적다면 코어 라이선스보다 저렴할 수 있다.

Microsoft 공개가 기준은 다음과 같다.

- Standard 서버 라이선스: $989
- 사용자 또는 장치 CAL: 개당 $230
- 코어 영구 라이선스 4코어: $7,890

아래 표는 기존 3배 성장 인프라 비용과 VAT를 포함한 단순 공개가 비교다.

| 방식 | 일시 라이선스 | 1년 차 합계 | 3년 합계 | 코어 구독 대비 3년 절감 |
| --- | ---: | ---: | ---: | ---: |
| 4코어 연간 구독 | 해당 없음 | $8,261 / 약 1,156만원 | $24,782 / 약 3,469만원 | 기준 |
| Server+CAL 10개 | $3,618 / 약 507만원 | $8,759 / 약 1,226만원 | $19,041 / 약 2,666만원 | 약 804만원 |
| Server+CAL 20개 | $6,148 / 약 861만원 | $11,289 / 약 1,580만원 | $21,571 / 약 3,020만원 | 약 450만원 |
| Server+CAL 30개 | $8,678 / 약 1,215만원 | $13,819 / 약 1,935만원 | $24,101 / 약 3,374만원 | 약 95만원 |
| 기존 적격 라이선스 활용 | 증분 $0 가정 | $5,141 / 약 720만원 | $15,423 / 약 2,159만원 | 약 1,310만원 |

공개가 기준으로 약 30 CAL에서 4코어 영구 라이선스와 초기 라이선스 금액이 거의 같아진다.

다음 조건에서는 Server+CAL을 적용하기 어렵거나 위험하다.

- 외부 고객이나 협력사가 직접 또는 간접으로 시스템을 사용한다.
- 사용자와 장치 수가 계속 늘어난다.
- 공용 계정 때문에 실제 접근자를 명확히 셀 수 없다.
- 웹 애플리케이션이 SQL Server 접속을 중계한다는 이유로 최종 사용자를 CAL 산정에서 제외하려 한다.

애플리케이션을 통한 간접 접속도 CAL 산정에서 자동으로 제외되지 않는다. 실제 견적에는 Microsoft CSP의 라이선스 검토를 받아야 한다.

### 3.3 EC2 약정 할인

DB와 앱 서버 사양이 확정되고 24시간 운영할 계획이라면 1년 또는 3년 Compute Savings Plans, Reserved Instance를 검토할 수 있다.

- 컴퓨팅 부분에서 연 약 90만~150만원의 절감 가능성이 있다.
- 실제 할인율은 약정 기간, 선결제 방식과 인스턴스 조건에 따라 달라진다.
- EBS, 공인 IPv4, 데이터 전송, SQL Server 라이선스에는 같은 할인이 적용되지 않는다.

계약 전 AWS Pricing Calculator 또는 실제 계정 견적으로 확정해야 한다.

### 3.4 데이터 수명주기 관리

오래된 이력 데이터를 저비용 보관소로 이동하면 EBS 비용을 줄일 수 있다. 다만 기존 조회 SP가 과거 데이터까지 직접 읽는다면 다음 작업이 필요하다.

- 보관 대상과 보존 기간 정의
- 운영 DB와 아카이브 DB 분리
- 장기 이력 조회 API 또는 배치 별도 구현
- 삭제·이관 후 복구 절차 검증

EBS 비용 자체는 전체 견적에서 라이선스와 DB 컴퓨팅보다 비중이 낮다. 데이터 보관 정책이 없는 상태에서 아카이빙만으로 큰 비용 절감을 기대해서는 안 된다.

## 4. 조회 성능 최적화 시 추가 비용

조회 최적화는 다음 순서로 진행한다.

1. Query Store, 실행계획, 대기 통계와 P95 응답시간을 측정한다.
2. 쿼리, 통계와 인덱스를 개선한다.
3. 반복 조회에 기존 Redis 캐시를 적용한다.
4. 필요하면 Redis를 별도 서버 또는 관리형 서비스로 분리한다.
5. 스토리지가 병목일 때만 gp3 IOPS와 처리량을 올린다.
6. 최적화 이후에도 CPU와 메모리가 부족할 때 DB 서버를 증설한다.

### 4.1 단계별 인프라 추가 비용

아래 금액은 기존 3배 성장 기본안에 더해지는 인프라 비용이다. 여러 단계를 동시에 적용하면 합산하며 개발·DBA 작업비는 별도다.

| 단계 | 적용 내용 | 월 추가 비용 | 연 추가 비용 |
| --- | --- | ---: | ---: |
| 0. 측정 | Query Store, 느린 쿼리, P95, CPU·메모리·IOPS 측정 | $0 | $0 |
| 1. 쿼리·인덱스 | 실행계획 수정, 통계, 복합·포함 인덱스, EBS 100~300GB 예비비 | 약 1.4만~4.2만원 | 약 17만~51만원 |
| 2. 기존 Redis 활용 | 현재 앱 서버 메모리 내 조회 결과 TTL 캐시 | $0 | $0 |
| 3A. 앱 메모리 확대 | `t3.medium` 4GB에서 `t3.large` 8GB 수준으로 증설 | 약 5만~7만원 | 약 60만~84만원 |
| 3B. 관리형 Redis | 단일 노드 또는 복제 구성으로 캐시 분리 | 단일 약 6만~10만원 / HA 약 13만~20만원 | 단일 약 72만~120만원 / HA 약 156만~240만원 |
| 4. gp3 성능 확대 | 예: 6,000 IOPS·250MB/s 또는 12,000 IOPS·500MB/s | 약 3.1만~9.2만원 | 약 37만~111만원 |
| 5. DB 8 vCPU·64GB | DB EC2와 SQL Server 코어를 함께 2배로 증설 | 약 70만~75만원 | 약 840만~900만원 |
| 6. 조회 전용 DB | 별도 4코어 DB 서버, SQL 라이선스와 1.1TB 저장공간 | 약 85만~90만원 | 약 1,020만~1,080만원 |

관리형 Redis, EC2 증설과 조회 전용 DB 금액은 계획용 범위다. 실제 노드, 운영시간과 계약 방식이 정해지면 AWS Calculator와 CSP 견적으로 확정한다.

### 4.2 인덱스 저장공간 비용

기존 견적의 gp3 단가 $0.0912/GB-월을 적용한다.

```text
월 추가 비용 = 추가 GB × $0.0912 × VAT 1.10 × 1,400원
```

| 추가 EBS | 월 VAT 포함 | 월 원화 | 연 원화 |
| ---: | ---: | ---: | ---: |
| 100GB | $10.03 | 약 1.4만원 | 약 16.9만원 |
| 200GB | $20.06 | 약 2.8만원 | 약 33.7만원 |
| 300GB | $30.10 | 약 4.2만원 | 약 50.6만원 |

인덱스는 저장공간과 INSERT·UPDATE·DELETE 비용을 늘리지만 SQL Server 라이선스를 늘리지는 않는다. 현재 1.1TB 계획에는 운영 여유가 포함돼 있으므로 실제 인덱스 크기와 디스크 여유를 확인한 뒤 증설한다.

### 4.3 캐시 적용 기준

캐시는 다음과 같이 변경 빈도가 낮고 반복 조회가 많은 데이터부터 적용한다.

- 공통 코드
- 메뉴와 화면 설정
- 권한 정보
- 기준정보와 선택 목록
- 계산 비용이 크지만 결과가 일정 시간 유지되는 집계 조회

다음 데이터는 캐시 적용에 주의한다.

- 실시간 재고
- 주문 상태
- 출고와 입고 처리 결과
- 마감과 정산 데이터
- 사용자 또는 권한별로 결과가 달라지는 조회

캐시 견적에는 다음 구현 범위를 함께 넣는다.

- 캐시 키 규칙
- TTL
- 데이터 변경 시 무효화
- 조직·사용자·권한별 캐시 분리
- Redis 장애 시 DB fallback
- cache hit ratio와 stale data 모니터링

### 4.4 gp3 성능 증설 계산

gp3는 기본 3,000 IOPS와 125MB/s를 제공한다. 추가 IOPS와 처리량은 용량과 별도로 과금된다.

| 예시 구성 | 추가 성능 | 월 추가 비용 범위 |
| --- | --- | ---: |
| 6,000 IOPS / 250MB/s | IOPS +3,000, 처리량 +125MB/s | 약 3.1만원 |
| 12,000 IOPS / 500MB/s | IOPS +9,000, 처리량 +375MB/s | 약 9.2만원 |

실제 단가는 서울 리전 AWS 견적으로 다시 확인한다. Disk Queue, read/write latency와 처리량이 병목이라는 근거가 있을 때만 증설한다.

### 4.5 DB 서버 증설이 가장 비싼 이유

SQL Server 코어 라이선스는 DB 용량이 아니라 할당된 코어 수를 기준으로 한다. 4 vCPU에서 8 vCPU로 올리면 다음 비용이 함께 증가한다.

- DB EC2 컴퓨팅 비용
- SQL Server Standard 코어 라이선스
- 필요하면 추가 EBS와 백업 비용

따라서 DB 서버 증설은 인덱스나 캐시보다 비용 영향이 크다. 쿼리와 인덱스 최적화 후에도 CPU 또는 메모리가 지속 포화될 때만 적용한다.

## 5. 권장 견적 패키지

| 패키지 | 구성 | 월 추가 비용 | 기본안 포함 월 합계 |
| --- | --- | ---: | ---: |
| A. 비용 최소 | Query Store, 쿼리·인덱스 개선, 기존 Redis, EBS 0~200GB | 0~2.8만원 | 약 96만~99만원 |
| B. 균형형 | EBS 100~300GB, 앱 8GB 또는 단일 관리형 Redis, 필요 시 6,000 IOPS | 약 10만~18만원 | 약 106만~114만원 |
| C. 고성능 | 관리형 Redis HA, 12,000 IOPS·500MB/s, DB 8 vCPU·64GB | 약 90만~105만원 | 약 186만~201만원 |
| D. 조회 분리 | 기존 DB 유지, 조회 전용 4코어 DB 추가 | 약 85만~90만원 | 약 181만~186만원 |

고객 견적에는 다음 방식으로 제시하는 것을 권장한다.

- 패키지 A는 기본 범위에 포함한다.
- 패키지 B는 선택 옵션으로 둔다.
- 패키지 C와 D는 운영 부하 테스트 결과에 따른 조건부 예비비로 둔다.
- DB 8 vCPU 증설 가능성을 별도 항목으로 명시해 최대 비용을 고객이 미리 확인할 수 있게 한다.

## 6. 일회성 작업비 산정 기준

아래 공수는 고정 견적이 아니라 범위 산정을 위한 계획값이다.

| 작업 | 예상 공수 | 비고 |
| --- | ---: | --- |
| 측정과 상위 쿼리 선정 | 3~5인일 | Query Store, 대기 통계와 P95 기준선 수집 |
| 쿼리·인덱스 1차 개선 | 3~7인일 | 상위 병목 우선, 회귀와 쓰기 성능 영향 확인 |
| Redis 캐시 설계·적용 | 5~15인일 | 대상 API 수와 무효화 복잡도에 따라 변동 |
| 부하 테스트와 튜닝 검증 | 3~7인일 | 운영 데이터량과 동시 사용자 시나리오 필요 |
| SP·API 인벤토리와 대표 PoC | 60~100인일 | 407개 고유 화면 SP 분류와 10~15개 대표 변환·동등성 시험 |
| SP → ORM 전면 전환, MSSQL 유지 | 1,500~3,000인일 | 959개 업무 API 중 SP 의존 747개 기준 계획 범위 |
| SP → ORM + PostgreSQL 전면 전환 | 총 1,800~3,700인일 | 스키마·데이터·인덱스·운영 전환을 포함한 계획 범위 |

기존 150~500인일 추정은 최신 전체 API·화면-SP 연결 인벤토리를 반영하기 전의 초기 범위였으므로 위 상세 산정으로 대체한다. 고정 견적은 대표 PoC 이후에만 확정한다.

## 7. 실행 순서와 승인 기준

### 1단계 — 기준선 수집

2~4주 동안 다음 지표를 수집한다.

- API P50, P95, P99 응답시간
- DB CPU와 가용 메모리
- IOPS, 처리량과 디스크 지연
- 가장 많은 총 실행시간을 사용하는 쿼리
- 쿼리별 실행 횟수와 평균 읽기량
- Redis hit ratio와 메모리 사용량
- 동시 사용자와 피크 시간대

### 2단계 — 무증설 개선

- 쿼리 실행계획 개선
- 불필요한 전체 조회 제거
- pagination 적용
- 복합·포함·필터 인덱스 검토
- 통계 업데이트와 파라미터 스니핑 점검
- API의 N+1 호출 제거

### 3단계 — 캐시

반복 조회와 변경 빈도가 낮은 API에 TTL과 무효화 정책을 적용한다. 캐시 적용 전후의 DB 실행 횟수와 P95를 비교한다.

### 4단계 — 저장장치

Disk Queue, 읽기·쓰기 지연과 IOPS가 병목일 때만 gp3 IOPS 또는 처리량을 올린다.

### 5단계 — DB 증설

최적화 후에도 CPU 또는 메모리가 지속 포화되고 목표 P95를 넘을 때 8 vCPU·64GB 견적을 승인한다.

## 8. 최종 권고

현 시점에는 MSSQL을 유지하되 라이선스 구매 방식을 다시 검토하고, 조회 최적화는 단계적으로 예산화하는 것이 가장 합리적이다.

1. 실제 운영 사용자, 장치와 외부 접근자를 집계한다.
2. CAL 대상이 20 이하로 확정되면 Server+CAL 병행 견적을 요청한다.
3. 고객사의 기존 SQL Server 라이선스와 AWS 반입 가능 여부를 확인한다.
4. 기본 견적에는 Query Store, 상위 쿼리 분석과 인덱스 개선을 포함한다.
5. 인덱스 공간에는 월 0~4.2만원의 EBS 예비비를 둔다.
6. Redis 분리와 gp3 성능 증설은 지표 기반 선택 옵션으로 둔다.
7. DB 8 vCPU 증설은 월 70만~75만원의 조건부 예비비로 별도 표시한다.
8. PostgreSQL 또는 Babelfish 전환은 라이선스 절감 외의 장기 목적이 있을 때 별도 프로젝트로 검토한다.

## 9. 전제와 확인 필요 사항

- 가격 기준은 기존 견적과 동일한 2026-08-28이다.
- 환율은 USD 1달러 = 1,400원이다.
- 원화 금액은 VAT 10%를 포함한다.
- DB 3배 성장 836GB, EBS 1.1TB, SQL Server Standard 4코어와 앱 `t3.medium`을 기준으로 한다.
- Vercel, 장기 백업, 재해 복구, 운영 인력과 데이터 전송 증가는 포함하지 않는다.
- 관리형 Redis와 EC2 약정 할인은 계획용 범위이며 실제 AWS 견적으로 확정해야 한다.
- CSP 할인, 기존 라이선스 적용과 CAL 산정은 Microsoft 파트너 검토가 필요하다.
- `BIZCLIENT` 용량과 Enterprise 전용 기능 사용 여부는 추가 확인이 필요하다.
- 피크 동시 사용자, 읽기·쓰기 비율과 목표 P95가 확정돼야 최종 성능 사양을 결정할 수 있다.
