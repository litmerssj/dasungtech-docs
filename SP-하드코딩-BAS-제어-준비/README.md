# SP 하드코딩 BAS 제어 준비

현재 운영 Stored Procedure에 직접 들어 있는 업무 코드, 기준일, 기간, 금액·수량·비율, 고정 참조값, 안내 문구 등을 백엔드 설정으로 옮기고 신규 BAS 화면에서 안전하게 관리하기 위한 사전 분석 자료다.

## 결론

SP의 모든 리터럴을 BAS 설정으로 옮기면 안 된다. 업무 정책과 기술 계약을 먼저 구분한 뒤, 확정된 업무 정책만 타입·범위·적용일·승인·이력을 가진 백엔드 설정으로 전환해야 한다. 비밀번호·암호키는 BAS가 아니라 비밀 저장소로, 빈 문자열·`%`·`0`·`1` 같은 검색/처리 센티널과 SQL 실행 상수는 원칙적으로 코드에 남긴다.

## 분석 기준

- 기준일: 2026-09-07 (Asia/Seoul)
- 운영 원문: `live-schema-20260824T064641Z` 읽기 전용 SQL Server 메타데이터 스냅샷
- 대상 DB: `MISCM`, `MISPD`, `MISSA`, `MISTO`, `MISTW`
- 대상 SP: 운영 스냅샷에서 확인된 1,815개
- 현재 화면 연결: `anasa-procedure-reverse-engineering/screen-flows/screen-sp.tsv`
- 백엔드 비교: `be_anasa`의 `develop` 브랜치
- 고객 데이터 행: 수집·분석하지 않음

운영 스냅샷은 2026-08-24 시점 자료이므로 그 이후 실DB 변경은 반영하지 않는다. 실제 이관 직전에는 읽기 전용으로 `OBJECT_DEFINITION`을 다시 수집하고 이 원장과 차이를 검증해야 한다.

## 판정 용어

| 용어 | 의미 |
| --- | --- |
| 후보 | 정적 분석에서 하드코딩처럼 보인 값. 업무 설정으로 확정된 값이 아니다. |
| 현재 화면 연결 | FE → BE → SP 호출 계보에서 현재 route의 caller가 확인된 SP다. |
| 운영/백엔드 일치 | 운영 스냅샷과 체크인된 SP 정의가 공백·대소문자를 제외하고 의미상 동일하다. |
| 운영 원문 우선 | 운영에만 있거나 백엔드와 다른 SP다. 배포 원천부터 확인해야 한다. |
| BAS 제어 적합 | 업무 담당자 변경이 허용되고 타입·범위·효력일·승인 규칙이 확정된 값이다. |

## 사용 순서

1. [현재 화면 연결 SP 우선 검토](./03-현재-화면-연결-SP-우선검토.md)에서 호출 중인 SP와 P0/P1 후보를 먼저 본다.
2. [후보 전수 목록](./후보목록/README.md)에서 해당 SP의 원문 문맥과 반복 위치를 확인한다.
3. 후보를 `업무 설정`, `공통코드`, `참조 마스터`, `비밀/환경설정`, `코드 유지`, `폐기` 중 하나로 판정한다.
4. `업무 설정`만 설정 키·타입·검증 범위·적용일·승인 정책을 확정한다.
5. 백엔드 해석기와 SP 파라미터화를 먼저 배포한 뒤 shadow 비교를 통과시킨다.
6. 마지막에 BAS 편집·승인·롤백 기능을 연다.

고객 확인 질문은 이 문서에서 자동 생성하지 않았다. 코드로 확정할 수 없는 업무 정책은 후보 판정 단계에서 별도로 합의해야 한다.
