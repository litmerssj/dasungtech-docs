# 분석·이관 검증 체크리스트

## 후보 판정

- [ ] 운영 원문을 이관 직전에 다시 수집했다.
- [ ] 운영/백엔드 불일치와 운영 전용 SP의 배포 원천을 확인했다.
- [ ] 같은 값이 여러 SP·화면에서 중복되는지 확인했다.
- [ ] 값이 업무 정책인지 SQL/API 기술 계약인지 구분했다.
- [ ] 기존 공통코드 또는 참조 마스터로 대체 가능한지 확인했다.
- [ ] 값의 업무 의미, 단위, 허용 범위, 효력 기간, 책임 영역을 확정했다.
- [ ] 고객 데이터·비밀번호·암호키·토큰을 일반 설정으로 분류하지 않았다.
- [ ] 미확정 항목을 사실처럼 작성하지 않았다.

## 백엔드

- [ ] 설정 키가 SP명·화면명 변경과 무관하게 안정적이다.
- [ ] 타입·범위·참조 무결성을 저장과 조회 양쪽에서 검증한다.
- [ ] 범위·효력 시점별 활성 버전이 하나만 존재한다.
- [ ] 설정 부재·중복·오류의 fallback 또는 fail-closed 동작이 명시되어 있다.
- [ ] 캐시 키에 설정 버전이 포함되고 적용·원복 시 무효화된다.
- [ ] 실제 업무 처리에 사용된 설정 버전을 로그에서 찾을 수 있다.
- [ ] 쓰기 API는 동시 수정 방지와 멱등성을 보장한다.
- [ ] SP를 호출하지 않는 배치·내부 SP 호출 경로도 누락 없이 처리한다.
- [ ] 비밀값은 전용 저장소에 있고 API·로그·오류에 출력되지 않는다.

## SP/업무 로직

- [ ] 기존 리터럴과 동일한 초기 설정 버전으로 시작한다.
- [ ] SP에 추가한 파라미터의 타입·길이·NULL 규칙이 기존 계산과 호환된다.
- [ ] 검색 센티널과 업무 코드값을 혼동하지 않았다.
- [ ] 날짜 경계, 월말·연말, 윤년, 시간대 기준을 테스트했다.
- [ ] 금액·비율·수량의 단위와 반올림 위치를 테스트했다.
- [ ] 조회뿐 아니라 INSERT·UPDATE·DELETE와 하위 SP 호출 영향도 확인했다.
- [ ] 기존값/신규값 shadow 결과 차이를 저장하고 승인했다.
- [ ] 실DB 쓰기 검증은 승인된 fixture와 격리된 환경에서만 수행했다.

## BAS 화면

- [ ] 후보와 확정 설정을 시각적으로 구분한다.
- [ ] 원문 SQL은 읽기 전용이며 기본 접힘이다.
- [ ] 현재 화면·API·BE handler·SP parameter 사용처가 표시된다.
- [ ] 현재값, 초안값, 타입, 단위, 범위, 효력 기간을 함께 비교할 수 있다.
- [ ] 임의 SQL·임의 실행식 입력을 허용하지 않는다.
- [ ] 활성값 직접 수정 대신 새 버전을 만든다.
- [ ] 승인되지 않은 버전을 적용할 수 없다.
- [ ] 영향 미리보기 없이 대량 적용할 수 없다.
- [ ] 비밀값은 화면 DOM과 네트워크 응답에 포함되지 않는다.
- [ ] 답변·판정·드롭다운 값이 재렌더·새로고침·원격 병합·내보내기에서 보존된다.

## 배포와 원복

- [ ] 설정 schema 변경과 애플리케이션 배포의 순서가 하위 호환된다.
- [ ] 구버전 애플리케이션이 신규 설정을 만나도 안전하다.
- [ ] 적용 실패 시 직전 정상 버전으로 원복할 수 있다.
- [ ] 원복도 새 감사 이벤트와 버전으로 남는다.
- [ ] 설정 저장소 장애와 캐시 장애를 각각 시험했다.
- [ ] 성능 기준과 cache hit/miss, 설정 조회 지연을 측정했다.
- [ ] 재고·마감·금액 쓰기 로직은 별도 승인과 복구 절차를 통과했다.

## 문서 갱신

- [ ] 기준 커밋, 운영 스냅샷 시각, manifest 해시를 기록했다.
- [ ] 후보 개수와 제외 규칙을 기록했다.
- [ ] 판정 결과와 근거 링크를 최신화했다.
- [ ] 운영 원문 재수집 후 추가·삭제·변경 후보 차이를 검토했다.
