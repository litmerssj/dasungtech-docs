# 백엔드 설정 모델 및 BAS 화면 요구사항

## 1. 목표

운영 중인 SP의 업무 정책값을 배포 없이 변경할 수 있게 하되, 임의 변경으로 조회·계산·재고·마감 결과가 달라지는 위험을 통제한다. BAS 화면은 SQL 편집기가 아니라 검증된 설정의 조회·초안 작성·승인·적용·원복 화면이어야 한다.

```text
BAS 관리 화면 → 설정 API → 정책 검증·승인 → 버전 저장
                                      ↓
업무 API → 설정 해석기 → 확정 버전 조회 → SP 파라미터 전달 또는 신규 BE 로직
                                      ↓
                              변경·사용 감사 로그
```

## 2. 이관 대상 판정

| 후보 유형 | 기본 처리 | BAS 편집 |
| --- | --- | --- |
| 기준일, 조회기간, 마감기간 | 적용 시작/종료일을 가진 정책 버전으로 이관 | 적합 가능 |
| 금액, 수량, 비율, 임계값 | 단위·최솟값·최댓값·반올림을 명시한 숫자 정책으로 이관 | 적합 가능 |
| 업무 코드·상태 | 기존 공통코드가 있으면 새 설정을 만들지 않고 참조 | 코드 관리 권한과 연계 |
| 고정 사번·거래처·품목·공정·창고 | 문자열 직접 입력 대신 참조 마스터 선택 | 제한적 적합 |
| 안내·오류 문구 | 메시지 카탈로그 필요성이 확인될 때만 분리 | 제한적 적합 |
| 비밀번호·암호키·토큰 | 비밀 저장소와 배포 환경으로 이동 | 금지 |
| 파일 경로·서버 주소 | 환경설정 또는 비밀 저장소로 이동 | 기본 읽기 전용 |
| 빈 문자열, `%`, `0`, `1`, `NULL` 센티널 | API/SP 계약으로 유지 | 기본 제외 |
| 날짜 포맷 코드, 자료형 길이, `EXISTS SELECT 1`, 오류 검사값 | 기술 실행 상수로 유지 | 제외 |
| 동적 SQL 내부 문자열 | SQL injection과 권한부터 수동 검토 | 직접 노출 금지 |

자동 탐지 우선순위는 검토 순서일 뿐 BAS 적합 판정이 아니다. 예를 들어 보안값은 P0이지만 BAS 편집 대상은 아니다.

## 3. 개념 데이터 모델

실제 테이블명은 백엔드 규칙에 맞춰 확정하되 다음 개념은 분리한다.

### 정책 정의

| 필드 | 설명 |
| --- | --- |
| `policy_key` | 변경되지 않는 영문 식별자. SP명이나 화면명이 바뀌어도 유지한다. |
| `name`, `description` | 업무 담당자가 이해할 수 있는 이름과 영향 설명 |
| `value_type` | string, integer, decimal, boolean, date, enum, reference, json 중 허용 타입 |
| `unit` | 일, 개월, 원, %, mm, 개 등 값의 단위 |
| `validation_rule` | 허용 범위, 정규식, 소수점, 허용 코드, 참조 대상 |
| `scope` | 전사·법인·사업장·모듈·화면·기능 등 적용 범위 |
| `owner` | 업무 책임 영역. 실제 역할명은 별도 합의가 필요하다. |
| `sensitivity` | 일반, 제한, 비밀. 비밀은 값 자체를 이 저장소에 두지 않는다. |

### 정책 버전

| 필드 | 설명 |
| --- | --- |
| `version` | 단조 증가 버전 |
| `value` | 타입 검증을 통과한 값 |
| `effective_from`, `effective_to` | 효력 기간. 중복 기간을 허용하지 않는다. |
| `state` | draft, review, approved, active, retired, rejected의 상태 머신 |
| `change_reason` | 변경 사유와 관련 작업 번호 |
| `created_by`, `approved_by`, `activated_by` | 작성·승인·적용 주체 분리 |
| `created_at`, `approved_at`, `activated_at` | 서버 시간 기준 감사 시각 |
| `previous_version` | 원복 가능한 직전 버전 |

### 사용처 바인딩

| 필드 | 설명 |
| --- | --- |
| `policy_key` | 정책 정의 연결 |
| `consumer_type` | SP parameter, BE rule, ORM query, batch 중 하나 |
| `database`, `procedure`, `parameter` | SP 사용처일 때의 정확한 대상 |
| `api_method`, `api_path` | 현재 호출 API 근거 |
| `transform` | 단위·형식 변환. 임의 실행식이 아니라 허용된 변환만 사용한다. |
| `fallback_mode` | 설정 미조회 시 fail-closed, 마지막 정상값, 코드 기본값 중 합의된 방식 |

### 감사 로그

조회·초안·승인·적용·원복·실제 업무 API 사용을 구분해 기록한다. 변경 전후 값, 사용자, 사유, 정책 버전, correlation ID, 사용 API/SP를 추적할 수 있어야 한다. 제한값은 마스킹하고 비밀값은 저장하지 않는다.

## 4. 백엔드 동작 원칙

1. 업무 API가 설정 해석기에 `policy_key`, 적용 범위, 업무 기준 시각을 전달한다.
2. 해석기는 현재 유효하고 승인된 단일 버전만 반환한다.
3. 값은 타입과 범위를 다시 검증한 뒤 SP의 신규 파라미터 또는 BE 로직에 전달한다.
4. 설정 없음·중복·형식 오류 때의 fallback은 정책별로 명시하며 조용히 임의 기본값을 쓰지 않는다.
5. 캐시는 버전 키를 포함하고 적용/원복 이벤트에서 무효화한다.
6. 실제 사용 버전을 업무 로그에 남겨 과거 결과를 재현할 수 있게 한다.

SP가 설정 테이블을 직접 읽는 방식보다 백엔드가 설정을 해석해 명시적 파라미터로 전달하는 방식을 우선 검토한다. 이렇게 하면 API별 범위·권한·캐시·감사·점진 전환을 한곳에서 통제할 수 있다. 단, 배치나 SP 간 내부 호출 때문에 백엔드를 통하지 않는 경로는 별도 adapter 또는 SP-side resolver가 필요하다.

## 5. API 초안

경로와 권한명은 미확정이다. 아래는 필요한 기능 계약이다.

| 기능 | 예시 | 주요 조건 |
| --- | --- | --- |
| 후보 목록 | `GET /api/v1/bas/sp-policy-candidates` | 모듈, 화면, SP, 분류, 우선순위, 연결 여부, drift 필터 |
| 정책 상세/이력 | `GET /api/v1/bas/sp-policies/{key}` | 값·사용처·버전·감사 이력 반환 |
| 초안 작성 | `POST /api/v1/bas/sp-policies/{key}/versions` | 타입·범위·효력기간 검증 |
| 영향 미리보기 | `POST /api/v1/bas/sp-policies/{key}/preview` | 영향 API/SP와 기존·신규 결과 비교, 쓰기 금지 |
| 승인/반려 | `POST /api/v1/bas/sp-policies/{key}/review` | 작성자와 승인자 분리 여부는 정책으로 확정 |
| 적용 | `POST /api/v1/bas/sp-policies/{key}/activate` | 승인 버전만 허용, 동시 활성 버전 금지 |
| 원복 | `POST /api/v1/bas/sp-policies/{key}/rollback` | 새 감사 이벤트와 새 버전으로 기록 |
| 사용처 조회 | `GET /api/v1/bas/sp-policies/{key}/usages` | FE route → API → BE → SP parameter 계보 |

변경 API는 낙관적 잠금용 버전 또는 ETag를 받아 동시 수정 유실을 막아야 한다. idempotency key, 요청자 권한, CSRF/인증 정책은 현행 백엔드 표준을 따른다.

## 6. 신규 BAS 화면

### 목록

- 모듈, 화면코드, 화면명, DB, SP, 설정명, 분류, 검토 우선순위
- 현재 화면 연결 여부와 API 수
- 운영/백엔드 일치, 운영 원문 우선 상태
- 후보 판정: 미검토, 업무 설정, 공통코드, 참조 마스터, 환경/비밀, 코드 유지, 폐기
- 적용 상태: 초안, 검토중, 승인, 적용, 종료, 반려
- 담당 영역, 최근 변경자, 적용 시작일

### 상세

- 원문 SQL 발췌와 행 번호는 읽기 전용·기본 접힘으로 표시
- route → API → handler → SP 사용처와 영향 화면 표시
- 현재 값과 신규 초안, 타입·단위·허용 범위·효력 기간을 나란히 비교
- 기존값/신규값 shadow 결과와 차이 요약
- 변경 사유, 승인 기록, 적용·원복 이력
- 비밀값은 존재 여부와 마지막 교체 시각만 표시하고 값은 표시하지 않음

### 동작 제한

- SQL 본문과 임의 식을 화면에서 직접 저장하지 않는다.
- 활성 버전 직접 수정 대신 새 버전을 만든다.
- 효력 기간 중복, 참조 마스터 미존재, 범위 초과는 저장 단계에서 차단한다.
- 삭제 대신 종료/폐기 상태를 사용해 과거 결과의 재현성을 보존한다.
- 대량 적용은 영향 미리보기와 별도 승인 없이는 허용하지 않는다.

## 7. 점진 이관 순서

1. P0/P1 후보를 업무 담당자와 판정하고 설정 키·타입·단위·범위를 확정한다.
2. 운영/백엔드 불일치 18개 SP의 배포 원천을 먼저 정리한다.
3. 읽기 전용 후보 조회 API와 BAS 목록/상세를 만든다.
4. 백엔드 설정 해석기, 버전·감사 저장소, 캐시 무효화를 구현한다.
5. 한 업무 흐름에서 SP 리터럴을 신규 파라미터로 치환하고 기존값을 초기 정책 버전으로 적재한다.
6. 일정 기간 기존 로직과 신규 설정 결과를 shadow 비교한다.
7. 차이가 승인 기준 안에 들면 신규 설정을 활성화한다.
8. 원복 훈련과 이력 재현을 통과한 뒤 다음 업무 묶음으로 확장한다.

첫 적용 대상은 현재 화면에서 호출되며, 값의 업무 의미와 책임자가 명확하고, 읽기 결과에만 영향을 주며, 과거 효력일이 분명한 후보가 적합하다. 재고·마감·금액 쓰기 로직은 후순위로 두고 별도 회귀 fixture와 원복 검증을 요구한다.

## 8. 완료 조건

- 후보가 설정/코드/공통코드/참조/비밀/폐기 중 하나로 판정되어 있다.
- 설정마다 고정 키, 타입, 단위, 범위, 적용 범위, 효력일, 책임 영역이 있다.
- 현재 활성 버전은 범위·시점별 하나뿐이다.
- 모든 변경은 작성·승인·적용·원복 이력으로 재현 가능하다.
- 호출 API와 SP parameter까지 사용처가 추적된다.
- 설정 조회 실패·중복·오류의 동작이 테스트로 고정되어 있다.
- shadow 비교와 회귀 테스트가 통과한다.
- 비밀값과 고객 데이터가 BAS 응답·로그·문서에 노출되지 않는다.
